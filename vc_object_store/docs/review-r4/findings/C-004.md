# C-004: Session region limits are consumed by geometry subsequently hidden by drafts/attachments

Status: code-traced candidate; independent-model validation pending. Priority P2. Baseline `2b5d1e01fd26f27b3410d1b024c3f10a73533287`.

Location: `vc_object_store/src/ObjectStoreSession.cpp:1179–1207`, `ObjectStoreSession::geometryRegion`.

Trigger: two stored surfaces A and B cross a slab, A sorts first, and query `maximumObjects=1`. A also has an editor draft moved outside the slab. The physical query returns A with `ObjectLimit`, before ever reaching B. The session then erases A's runs because A has a draft; the draft has no intersection. The final session result contains no surface although visible B should fill the available slot. The same problem occurs when an earlier attachment shadows A outside the slab and a later attachment's limited query consumes its slot on old A.

`selectObjects` in the same session already refills pages after shadowed candidates, whereas region merging filters only after each backend has stopped. Region `intersectingObjects` is also left at the unfiltered count, potentially reporting one intersecting object beside zero runs. Work/byte statistics may truthfully include rejected candidates, but the visible intersection count should not.

Required behavior: shadowed or draft-replaced stored objects must not consume the final visible-result object limit. Preserve query budgets and incompleteness reporting instead of silently dropping the remaining visible candidates.

Shared fix direction: express exclusions/precedence before backend limit selection, or add a shared bounded continuation/refill mechanism for session region queries. Do not perform an unbounded full-geometry fallback or invent a consumer-specific second query.

Evidence: code trace only. Regression needed for local and hosted attachments where supported: max1 with draft A outside/B inside; earlier attachment A outside/later old A and B inside; verify B present and final object counts match returned runs while spent-work statistics remain accurate.

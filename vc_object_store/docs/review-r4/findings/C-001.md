# C-001: Exact attached-document reads depend on unrelated attachment history

Status: speculative reachability candidate; independent-model validation pending, **do not count as confirmed**. Tentative priority P2. Baseline `2b5d1e01fd26f27b3410d1b024c3f10a73533287`.

Location: `vc_object_store/src/AttachedDocument.cpp:169–180`; shared expansion at `src/relationships/Traversal.cpp`, `StoreReader::graphReadViewAround`.

Trigger: a selected surface has a retained document in requested role A and a document in unrelated role B. B belongs to a history-off owner and is later edited so its original referenced version is unavailable. Read `attachedDocument(reader, selectedSurfaceReference, "A")`.

The helper expands the entire attachment-kind component before filtering the requested role. `graphReadViewAround` resolves every recorded endpoint in each subsequent frontier and throws when B's old endpoint is missing. Consequently A cannot be read even though A and the selected surface are retained and internally consistent. Multi-hop unrelated attachment branches cause the same dependency. VC3D `CWindow::loadLasagnaResults` calls this selected-owner overload, so unrelated correction/growth evidence can block the requested Lasagna document.

Required behavior: selected document reading must preserve exact recorded endpoint versions, but only the relationship(s) needed for the requested owner/role should determine availability. This is not permission to substitute current B or bypass applicability validation. The generic graph closure's documented fail-closed behavior is correct; the document helper asks it to resolve too broad a graph.

Shared fix direction: expose filtered/one-hop recorded attachment selection at the shared reader/graph layer and use it before expanding/resolving unrelated endpoints; do not add document-specific SQL or history-off fallback branches.

Evidence: code trace only, no runtime probe run in this inspection. Regression needed: role A remains readable through local/referenced source cases after unrelated B loses its old history-off version; requesting B still fails explicitly.

Author's negative check: the proposed retention trigger is not yet established through supported APIs. Referenced history-off stores must be sealed, so B cannot simply be edited in place. A local history-off store also does not retain ordinary old surface states, while normal writes may revalidate the attachment binding. The second reviewer must first establish a legal graph where the unrelated endpoint is genuinely unavailable; otherwise reject this finding as an intentional fail-closed closure/capability boundary, not a current bug. The overly broad traversal alone does not prove a correctness defect.

# S-004: Umbilicus stamped dimensions narrow without a range check

Priority: P3. Baseline: `2b5d1e01fd26f27b3410d1b024c3f10a73533287`. Status: code-traced input-boundary defect; no runtime test executed.

`vc_object_store/src/UmbilicusFile.cpp:98–105` accepts any positive JSON integer as a stamped dimension, then converts `int64_t` to `int` without checking representability. The public `UmbilicusFile` stores these dimensions as `optional<int>`. On the supported conventional 32-bit-int platforms, a dimension such as 4,294,967,297 can become 1 without adding `metadataErrors`. The three dimension fields can consequently represent a different, apparently valid grid from the file's declaration; `umbilicusBinding` uses them to derive/check coordinate scaling.

Expected: reject a dimension outside the supported representation (through the existing malformed-frame error path), or use an explicitly wider dimension representation throughout. Do not silently narrow source geometry metadata. This is an oversized-input case, not evidence of failure on an ordinary current Paris4 grid.

Shared fix/regression: add a checked conversion in the common `readFrameMetadata` parser; test `INT_MAX`, `INT_MAX+1`, `2^32+1` and the largest JSON integer accepted by the parser, including a complete dimension triplet. Callers importing JSON and GUI previews should see the same refusal rather than a wrapped dimension.

Cross-model validation: pending.

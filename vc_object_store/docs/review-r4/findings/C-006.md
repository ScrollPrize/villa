# C-006: Duplicate active SQL statements leak when returned to the shared statement cache

Status: code-traced candidate; independent-model validation pending. Priority P2. Baseline `2b5d1e01fd26f27b3410d1b024c3f10a73533287`.

Location: `vc_object_store/src/internal/Sqlite.cpp:183–193`, `Statement::~Statement`; reachable nested reader construction in `src/geometry/GeometryReader.cpp` delta materialization/reverse-source branches.

Trigger: two statements with identical SQL text are simultaneously alive on one leased connection. Both are legal and own distinct `sqlite3_stmt*` handles because the first is active rather than idle. On destruction the inner statement inserts its handle into `pool_->idle`. The outer statement then calls `idle.emplace(sql_, value)` with that same key. Insertion returns false, but the destructor returns unconditionally instead of finalizing the rejected handle.

The lost handle is neither in the idle pool nor finalized. Repeating this leaks prepared statements and their SQLite allocations; eventual connection close can return busy because untracked prepared statements remain. Public historical delta reads can nest identical materialization-query statements: the historical GeometryReader keeps its materialization `Statement current` alive while constructing its reverse-source GeometryReader, which constructs the same SQL query for another revision. This is not a request for concurrent use of a transaction.

Shared fix direction: return only when cache insertion succeeds; finalize the duplicate/rejected handle. Keep capacity and exception handling in the existing shared Statement wrapper, with no caller-specific query rewrite.

Evidence: code trace only. Regression should construct duplicate simultaneous statements, then compare `sqlite3_next_stmt` before/after pooled teardown; include repeated historical reverse-delta reads and verify no growth. No production changes or runtime probe in this review.

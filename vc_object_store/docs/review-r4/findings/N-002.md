# N-002: CLI surface updates omit the loaded volume-mapping guard

Priority: P2. Baseline: `2b5d1e01fd26f27b3410d1b024c3f10a73533287`. Status: code-traced; no runtime reproduction run.

## Location and trigger

`volume-cartographer/core/src/StoreSurfaces.cpp:28–37` transforms a selected surface into requested volume voxels, but retains only the pin and an identity Boolean through `ToolObjects::noteRead` (`vc_object_store/src/ToolObjects.cpp:34–37`). `StoreSurfaces::update` at lines 57–74 uses `viewStored` and guards only the selected object reference plus relationship endpoints. It does not append a `CheckVolumeMappingOp` or otherwise compare the loaded mapping.

The production caller `ObjAlphaCompRefinement.cpp:395–404` loads a surface with `options.volume`, performs the potentially long refinement, then updates the original object. For a surface in volume A registered identically to requested volume B, the writable identity check passes. Another writer changes that registration to a translation while refinement runs; the surface object version remains unchanged. The result expressed in the old B frame is then committed as stored A coordinates without detecting that the interpretation changed.

## Required behavior

Loaded coordinate mappings must accompany editable points and be checked atomically when saving. An unchanged source object reference does not establish that volume registrations are unchanged. This is the CLI sibling of the GUI mapping guards, not a request to permit nonidentity edits already rejected by the tool.

## Shared fix direction and regression

Retain the existing shared mapping-check operation alongside the loaded tool pin and use it for updates, rather than rebuilding an unrelated current mapping or adding CLI-only SQL. Test an initially identity registered mapping changed without changing the surface, plus an unrelated registration change that preserves the actual mapping. The former must reject before mutation; the latter may succeed.

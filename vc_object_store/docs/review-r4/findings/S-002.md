# S-002: Direct object-copy helper leaves partial writes after a caught failure

Priority: P2. Baseline: `2b5d1e01fd26f27b3410d1b024c3f10a73533287`. Status: code-traced public C++ API; no runtime probe executed. No in-repository production caller currently uses this helper.

## Location and trigger

`vc_object_store/src/ObjectCopy.cpp:56–61`, `writeObjectCopy`, first calls `upsertObject`, then `putGeometry`, without one operation-wide savepoint. `objects/ObjectCopy.hpp:21–22` describes it as the same copy operation inside a caller's write transaction.

A caller can pass a copy with valid metadata but invalid typed geometry, catch the geometry exception, then commit its outer write transaction. Each primitive guards only its own operation: the object insertion or metadata replacement already completed by `upsertObject` remains committed, despite the copy operation failing. This is the same reachable failure pattern that R3 fixed in surface/umbilicus/catalog composite helpers, but this sibling was omitted.

## Required behavior and shared fix

The complete public composite copy must roll back on failure even when the caller catches the exception and commits its transaction. Wrap the existing primitive calls with the common `Savepoint`, including transaction-local bookkeeping rollback; do not introduce a separate copy transaction engine. Test both a fresh destination object and an existing object with geometry publication rejected, then explicitly commit the surrounding transaction and check that its pre-call state survives.

This finding does not assert that absence of an in-repository caller makes the public API safe, nor does it claim a current GUI data-loss reproduction. It concerns the directly exposed C++ contract.

Cross-model validation: pending.

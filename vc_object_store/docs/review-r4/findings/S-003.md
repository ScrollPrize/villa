# S-003: Hosted exact-version disk cache makes missing future versions permanently missing

Priority: P2. Baseline: `2b5d1e01fd26f27b3410d1b024c3f10a73533287`. Status: code-traced; no runtime probe executed.

## Location and trigger

`vc_object_store/src/HostedSession.cpp:587–590` publishes the literal `null` to disk when the server's exact-version batch response has no record. The key at line 31 is only store/generation/object/version, with no observed commit. Lines 533–545 subsequently accept that cached `null` and remove the request from the server-fetch list. Refresh invalidates current-head memory entries, not this disk entry (`invalidate`, lines 359–364).

Attach a history-enabled hosted store with disk caching. Request a valid object's next numbered version before the corresponding edit; the batch API correctly returns no record at that moment. Perform the edit so that the same generation/object/version now exists, then refresh and request it again. The server/local reader can return the revision, but the cached attachment continues returning no record, including after reopening with the same cache. R3 fixed graph-cache membership freshness, but this negative exact-version cache has the same mutable-absence problem.

## Required behavior and shared fix

An existing exact revision is immutable; absence is not immutable while that lineage can still publish the requested version. Do not persist negative results under an immutable revision key, or make negative entries freshness-scoped and invalidate them through the common observed-commit mechanism. Preserve ordinary positive immutable payload caching and overlapping-fetch coordination.

Regression: query version `head+1` before/after publication through a disk-cached attachment and an uncached reader, refresh, and reopen the cache. All readers must agree once the version exists. Test current-lineage history on and the applicable current-only case without claiming that unavailable discarded versions become available.

## Author objection after tracing the shared publication helper

Rejected by the author on further review: `HostedAttachment::publishPayload` at HostedSession.cpp:113 explicitly returns for bytes equal to `null`. Therefore the proposed fetch path never persists the negative result, and the next request fetches it again. The earlier description omitted that common helper and does not establish a reachable defect. Retained for the audit trail; do not fix or count as an accepted finding. Cross-model reviewer was notified by the primary agent.

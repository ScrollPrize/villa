# C-003: Tool artifact publication discards the loaded complete revision and write generation

Status: code-traced candidate; independent-model validation pending. Priority P2. Baseline `2b5d1e01fd26f27b3410d1b024c3f10a73533287`.

Location: `vc_object_store/src/ToolObjects.cpp:18–31`; `src/ObjectStoreSession.cpp:391–429`.

Trigger: a long-running tool calls `noteRead(pin,...)`, computes an artifact, then the store's active history generation changes (or its visible owner changes to a same-number revision). Calling `ToolObjects::publishArtifacts` extracts only `pin.version` and sends it to the numeric session publisher. The publisher creates a fresh request from the current store generation and checks only current numeric version.

Unlike `ObjectStoreSession::requireCurrent(pin)`, publication can succeed after the loaded editor/tool pin's write generation is invalidated, and cannot distinguish same-version owners/lineages. It reads/merges the new head's manifest and publishes output computed from the earlier selected state. The header explicitly promises publication expects the version the tool read; the core contract requires complete source identity and loaded write guards.

The numeric session convenience API intentionally supports current publication across a history-generation reset (`test_object_store_artifacts.cpp:185–209`), so that existing test is not evidence that the loaded-tool path is safe. The loaded ToolObjects path must preserve the full pin rather than apply the convenience method's current-state semantics.

Shared fix direction: a complete-pin/reference-aware artifact preparation/publishing API, guarded through uploads and final submission, used by ToolObjects; preserve numeric convenience behavior for explicitly current publication if desired. Do not just call requireCurrent then submit an otherwise unguarded numeric request.

Evidence: code trace, not runtime-reproduced. Regression needed: generation reset invalidates a loaded-tool artifact write while an explicitly current publisher still works; equal-number source changes must reject too. Existing content-addressed uploads may remain harmless unreferenced blobs on conflict.

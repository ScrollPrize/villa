# N-004 — Receipts expose a second reference wire form

Status: candidate for independent adjudication; source-traced at `38c72d972`, not runtime-tested.

`src/Versions.cpp:246–275` (`detail::receiptToJson`/`receiptFromJson`) encodes `TransactionReceipt::objectReferences` as JSON arrays `[store,generation,object,version]`, by serializing with `versionReferenceText`, reparsing, dumping each input value, and parsing it with `parseVersionReference`. The standard reference codec in `Wire.cpp:16–25` uses `{store,generation,object,version}`. Thus a receipt's reference has a second public/persisted representation even though its native value is already `ObjectVersion`.

Producers: native transaction receipts and request replay. Sibling consumers: `transactionReceiptToJson`/`transactionReceiptFromJson` in `Commands.cpp`, hosted request receipts and request pages, Python receipt conversion/helpers in `python/objects.cpp`, and durable draft receipt recovery (`DraftCheckpoints.cpp` / session acknowledgement/recovery). Native `TransactionReceipt::objectReference` correctly returns the complete value and checks UUID consistency; retain that behavior. This finding concerns representation/conversion, not receipt owner correctness.

Simplification: emit the standard object form through one shared native reference codec; accept old array-valued receipt entries only at the receipt decoder and normalize immediately into `ObjectVersion`. Do not change persisted old receipts or infer missing owner fields from receipt store/generation. Maintain the documented reload requirement for old receipts that have no complete references.

Validation needed: native/wire/Python/hosted receipt parity, replay of stored array-form receipts, absent-reference legacy receipts, unchanged inherited inputs, canonical UUIDs, and draft recovery with successful/ambiguous acknowledgement. These paths are source-traced only.

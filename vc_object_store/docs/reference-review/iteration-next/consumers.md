## NX-P01 — link-marker read rebuilds a handle from a numeric receipt projection

**Low, reference-contract duplication; pre-existing, not a regression of the three working fixes.** `spiral-fitting/object_store_inputs.py::submit_link_plan` line2259 takes the link marker's number from `receipt['objects']` and passes it plus the request to `_link_marker_at` (2311–2324). That helper constructs a new `{store:request.store, generation:request.generation, object:link_marker_uuid(), version:int(number)}` before calling `objects_at_versions`. The receipt already has canonical complete object references, and `_refresh` in this same file (2598–2601) correctly uses shared `receipt_object_reference` to repin its other inputs.

This bypass is precisely a numeric/full sidechannel that the single-reference contract excludes: consumers should carry the receipt's complete selected reference, not reconstruct it from the committing request. There is no requirement for a link marker to use a different handle format. One shared selected metadata reader can accept the full reference returned by the existing receipt helper, removing the number/request interpretation. Do not add a compatibility fallback or another marker-specific codec.

**Bounded impact:** source trace of `src/linking/LinkObjects.cpp:375–389` shows the ordinary LinkObjects operation publishes the marker itself and advances its metadata `commit_sequence`. In that normal path it belongs to the committing root/lineage, so today's reconstruction normally selects the intended object. No wrong geometry, lost identity, authorization problem or inherited-marker runtime failure is demonstrated by this lane. This is a concrete contract/duplication issue, not a claim that all numeric display fields are broken. Astra may reject it as acceptable boundary reconstruction only with an explicit reason; it must not be described as a proven incorrect-owner counterexample.

**Attribution:** the exact numeric call and helper exist in `b73a31f33`; neither the new strict scalar parsing, tombstone import refusal nor UUID scope normalization introduced it. It was missed by the previous consumer trace. This is one finding including the producer/caller/helper/sibling chain, not multiple counts.

**Suggested regression if accepted:** an ordinary local and hosted refresh must exact-read the marker using the receipt's full reference and preserve report matching; missing complete receipt identity should fail through the shared helper, not reconstruct from `objects`. A unit spy can assert that `objects_at_versions` receives the identical shared receipt reference. Native LinkObjects publication and unrelated input repinning must stay unchanged. No new runtime test has been run in this review lane. The root assigned this candidate NX-P01 so cross-lane references use one stable ID.

## Scalar and exception distinctions not promoted to findings

- `SpiralServiceManager` JSON progress/event/UI counters and fit preview generation numbers are not vcobj ObjectVersion fields. They are not rewritten merely because they use `toInteger`/`toInt`.
- `object_store_inputs::changes_after` reads the change-feed boundary (store/generation context plus emitted version); those feed fields are native values. This is not the same as throwing away an already available complete receipt reference. No malformed feed authorization counterexample is claimed.
- `plan_link_refresh` interprets a custom LinkObjects marker's own metadata counters as application refresh-cache provenance, not a native object selector. Hardening arbitrary manually edited marker metadata could be considered separately; it is not added as a duplicate of native position validation without a demonstrated stale-link decision.
- Local current-object discovery for an explicit user restore, output artifact publication or source listing remains legitimate. It is not equivalent to replacing the selected state of an already-loaded input.

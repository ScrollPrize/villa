# Independent adjudication of root consumer candidates

Reviewer: Astra. Source baseline `153c9a10f1cca90f57a2e70dc5458d1bd5bad2a4`; no production changes or execution. Read the named implementations, their headers/docstrings and relevant native siblings. The behaviors below also exist at `0c7e4e521`; none is a newly introduced AF fusion regression.

## C01 — Fiber selection versus coordinate conversion

**Accept a narrower correctness finding; do not assume arbitrary affine support is promised.** `vesuvius/.../annotations/fiber_store.py` explicitly documents fibers bound to the requested volume, scalar `scale_factor`, and exclusion of fibers not bound to that volume. `_read_rows` and `FiberStore.geometry` consistently implement that scalar-only application contract. An explicit request for an other-volume fiber may therefore legitimately be refused; its refusal alone is not a defect requiring an affine feature expansion.

The real inconsistency is `fiber_volume`: it promises to raise when fibers are bound to multiple volumes, but calls native `unbound_object_count`, whose `Queries.cpp::unboundObjectCount` treats a registration route as bound-to-target. With fiber A directly bound to volume X, fiber B bound to Y and a Y→X registration, the function can return X as the purported single binding volume. The following default `read_polylines`/catalog volume query includes B through registration, but `_read_rows(..., require_lines=False)` silently drops B because `geometry_scale_to_volume(B.meta, X)` is None. Thus a helper promising all fibers share one direct binding certifies a store whose default data read silently omits some fibers. Selection semantics and conversion semantics must agree.

Safe scoped alternatives: explicitly keep the documented direct-binding-only contract and validate/select it coherently through shared native coordinate APIs, or deliberately expand the application to registered affine inputs and carry the selected affine through catalog, geometry and block paths. The second is a feature/semantic change, not the only correctness repair. Do not add a Python SQL resolver or quietly change training coordinate semantics. Runtime diagnostics should distinguish an explicitly requested unsupported fiber from false default-volume certification.

## C02 — No-op surface update skips loaded guards

**Accept as a checked-operation contract gap, medium priority; do not describe as stored-data corruption.** `StoreSurfaces::update` obtains the loaded full-reference and mapping guards through `ToolObjects::writable`, computes changes against the loaded geometry revision, but returns the loaded numeric version when no edit was appended, without submitting any guards. A metadata-only external object edit or mapping registration change can leave that loaded payload unchanged; the old request is then reported as a successful no-op without validating the loaded selection or mapping. A real edit follows native transaction expectation/mapping validation instead.

The header explicitly says it returns the loaded version when nothing changed, so the problem is not merely that the returned counter is old. It is that the same checked update API bypasses all validation only on its no-op branch, despite retaining guards for precisely these concurrent changes. Validate the checked request without manufacturing an override/version bump. Preserve no-op identity/ownership and avoid turning a no-op into a write. Existing shared transaction validation is the owning layer; a consumer's second fresh numeric lookup is not a substitute.

## C03 — ToolObjects retains original pins after successful writes

**Do not classify automatic repinning as a required correctness fix on current evidence.** `ToolObjects.hpp` describes revisions the tool read; `publishArtifacts` explicitly expects the version read, and `writable` likewise uses that loaded baseline. `StoreSurfaces.hpp` is a command-line tool helper, not documented as a reusable interactive editing model. The identified actual `ObjAlphaCompRefinement` path performs one load/compute/update. A second changed update after the first is rejected because the caller has not reloaded; this is conservative, not silent overwrite.

Automatic receipt-only repinning could incorrectly bless an artifact computed from the original geometry as belonging to the post-update geometry. It also would not update the old lazy channel loader or reset the geometry/mapping baseline. A reusable editor API can be valuable, but should expose an explicit accept-committed-state/reload operation and coherently refresh all state. To elevate this to a correctness finding, identify an existing supported workflow requiring repeated writes or post-update artifact publication without reload, or establish that the public contract promises such reuse. At present classify as documented loaded-baseline behavior / optional API usability extension, not a proven defect.

## C04 — Duplicate object identities in saved manifests

**Accept as malformed-input validation inconsistency, lower priority.** `validated_manifest_references` decodes every reference but constructs its object result by dict comprehension, so duplicate object UUIDs (including object versus outer-shell collision) overwrite earlier complete references. `InputPins.from_manifest` then separately derives selection membership from all entries, so one retained reference can represent conflicting saved evidence. Relationship entries explicitly reject duplicate UUIDs through `seen`.

Reject duplicate object IDs at the shared manifest ingress, including duplicates with equal references unless explicitly defined as valid by the manifest contract. Do not infer that the last entry is authoritative. Native exact graph selection already rejects duplicate objects, but not every validation/comparison consumer constructs a graph, so downstream graph refusal does not close ingress validation. Test conflicting references, identical duplicate entries and outer-shell collisions. This is not an ordinary valid-manifest regression or proof that existing solver output emits duplicates.

## PF-A05 — Generation-only selector significance

**Retain PF-A05 as a genuine ignored-input issue, not removal of legitimate current discovery.** The permitted convenience selector is a version number within the current owner's history, optionally qualified by generation. `selectedObject(uuid, nullopt, generation)` receives an explicit lineage qualifier but has no numbered version to qualify; silently treating it as an unqualified current request ignores user input. Python export explicitly enters its selection branch when generation is supplied, increasing the misleading behavior. A wrong/malformed generation currently produces current data rather than an error.

The fix is only to reject generation without version at the common selector. Version-only convenience discovery and no-argument current discovery remain legitimate. Full-reference exact reads remain independent of live current heads. This is an input-contract issue, not evidence of valid full-reference misrouting.

## C05 — Native-loaded source frames collapse to nullopt

**Accept as a public helper contract gap, medium priority, with limited demonstrated application exposure.** `ToolObjects::coordinatesFor` compares only `Read::volume` values. Two sources loaded in native/stored coordinates both contribute nullopt even if their retained selected metadata declares different volumes or different scale factors within the same volume. It then returns the first source's retained coordinate declaration without inspecting the second. The same implementation exists at `0c7e4e521`.

Both `ToolObjects.hpp` and `StoreSurfaces.hpp` explicitly say sources read in different frames throw. The phrase “else the first source's binding” describes how an output binding is chosen, but does not clearly waive that consistency requirement. When sources are in the same native frame, selecting the first equivalent declaration is reasonable; it does not justify treating every native frame as identical. Example: load A with `{volume_uuid:X, scale_factor:1}` and B with `{volume_uuid:X, scale_factor:2}` using no target volume, then call `coordinatesFor({A,B}, nullopt)`. The helper accepts and labels output in A's stored frame even though B's coordinates use different units. Distinct declared volumes produce the same problem.

Evidence limits: the inspected CLI producers generally pass zero or one source to `create`; `vc_grow_seg_from_segments` loads multiple inputs but its publish lambda records only the selected individual source and commonly supplies an explicit volume. No concrete shipped multi-source output corruption is claimed from those callers. The public helper accepts a vector and advertises cross-source validation, so its direct supported multi-source case still warrants a regression.

Fix direction: compare effective frames for all *loaded* sources, using their retained complete references and shared `geometryCoordinates` normalization for native declarations, versus the explicit target frame when loaded through a volume view. Do not reread moving current heads or reconstruct coordinate policy ad hoc. Keep explicit output-volume override behavior as documented. Decide unknown/unbound declarations explicitly rather than asserting that null metadata establishes a common frame. Add same-binding/same-scale acceptance, scale mismatch, volume mismatch, and retained metadata after later head changes; preserve the existing single-source retention test in `test_coherent_store.cpp`.

# C-004 — Mixed-history ordering regresses in the reverse creation order within one second

Candidate P2; source-traced regression from the R5 S-008 patch. `Project.cpp:15–41` combines microsecond first-publication times with `createdAt` parsed as the *start* of its recorded UTC second. Ordinary record creation calls `nowIsoUtc` (`internal/RecordSql.cpp:425`; implementation `internal/Sqlite.cpp:92–106`) which retains whole seconds only, whereas history publication uses microseconds (`History.cpp:646–655`).

Trigger: add A in a history-on base, seal/reference it and add B in a history-off overlay, all in the same UTC second with A's publication occurring at a nonzero fractional second. B's coarse creation timestamp always sorts before A's earlier precise publication, although A was actually added first. At HEAD the old separate-domain key always put the history-on resource first, which was correct for this ordering (while failing R5's inverse fixture). R5's regression fixture tests only older history-off plus later history-on, at `tests/cpp/test_object_store_project.cpp:55–63`.

Expected: Do not treat a coarse timestamp as precise evidence of precedence. Define stable ordering for ambiguous same-second records, preserving known chronology where available (e.g. use recorded precision and an explicitly documented tie policy, or preserve a precise creation stamp for new records). Test both mode directions with same-second times; do not claim an exact cross-owner ordering for legacy records when chronology was never recorded.

Sibling closure: `projectResources` and `projectRecord` both call this sorter, so Python list/read, native session readers and copy/rename project selection inherit the behavior. The analogous old project-record branch gave missing history numeric zero, so the baseline-correct/newly-wrong attribution is for resource listing, not project selection. This is distinct from C-001 (which uses the wrong event even with perfect precision). Not runtime-tested.

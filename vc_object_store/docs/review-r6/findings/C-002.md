# C-002 — Metadata edits can silently change a project resource's identity and visibility

Candidate P2, source-traced. The identity key is the tuple (kind, location, owner) in `Project.cpp:163–185`; the viewer filter trusts the owner in metadata at lines 152–157. The native public `updateProjectResourceMeta` (lines 218–230) merges arbitrary keys, including `owner`, then updates the same UUID. Unlike construction, this path does not reserve the owner key. Its checked write pins the record revision but does not validate resource identity.

Trigger: add a resource for owner Alice, then call `updateProjectResourceMeta` on its returned UUID with `{"owner":""}`. The same resource now appears to every viewer as shared. Adding the same location for Alice again finds the Alice tuple's deterministic UUID and repurposes it back to private, rather than creating a separate private resource alongside the shared one. Conversely, moving a shared resource to Alice via metadata and then adding the legitimate Alice tuple can create duplicate visible resources. Viewer visibility is application selection, not a security authorization boundary.

Expected: ordinary resource metadata editing must preserve the tuple and its visibility, or a separately specified identity-change operation must create a coherent new key. The add path already makes the owner argument authoritative over metadata after R5. Python exposes add/list but no matching specialized metadata method; generic record operations are a distinct lower-level path. Native local and hosted sessions delegate the checked update; overlay behavior is source-traced via ordinary override preparation. Regression: add shared/private variants, try an owner-changing metadata patch and verify stable IDs and Alice/Bob views, then perform ordinary non-identity metadata edits.

Attribution: HEAD also merges owner metadata without checking it. This is not the same trigger as R5 S-009 (ambiguous concatenation on creation) nor a new R5 regression. No runtime test executed.

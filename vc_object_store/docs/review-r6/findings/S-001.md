# S-001 — Computed project-resource UUID no longer identifies legacy resources

Priority: P2. R5 regression (dirty overlay against `bea32d5d807731d8c3b2db17c815cde748523226`); source-confirmed.

`Project.hpp:65–66` promises the resource UUID is the same in every store. In the R5 overlay, `Project.cpp:164–166` always derives v2, but `resolveProjectResourceIdentity` (188–198) selects the old key for a matching persisted record. Therefore the same tuple can name two different object UUIDs depending on which store holds it. `addProjectResource` (201–215) writes the resolved old key; `updateProjectResourceMeta` and `removeProjectResource` (218–242) resolve only the UUID passed by the caller. A previously successful helper → update path now throws; helper → remove returns false. For example, open a store containing an ordinary legacy resource, call add with the same tuple, then remove by `projectResourceUuid`; the old resource is still listed. HEAD used one legacy key in all these paths (and separately had the R5 delimiter collision).

Sibling closure: local and hosted session adds share the resolver above; Python `objects.cpp:1087` exposes the pure v2 helper, while `objects.cpp:1661–1664` also writes the resolved old UUID. Lists return the actual UUID, so callers retaining a listed UUID are unaffected. A caller that builds a record with `projectResourceRecord` and directly calls native upsert still gets v2; the updated header's assertion that this record is what add writes is not true on legacy data. Generic UUID lookup and retire in Python likewise only know the provided identity. History policy is irrelevant to an ordinary live legacy row; collection copies retain that row.

Direction: make tuple-to-stored-reference resolution explicit and use it at all tuple-based lookups/writes, or provide an identity migration with a defined compatibility contract. Do not blindly remap by the ambiguous legacy key. Regression matrix: legacy and new stores, equal tuple in both, deliberate delimiter collision, retired restoration, helper-driven update/remove, local and hosted, Python plus native. R5's distinct-new-ID test does not exercise this compatibility failure. None run in this lane.

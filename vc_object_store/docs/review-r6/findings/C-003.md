# C-003 — Python project add does not reactivate an existing retired resource

Candidate P2, source-traced. Python `ObjectStore.add_project_resource` directly calls `upsertObject` (`python/objects.cpp:1659–1665`) while native `addProjectResource` explicitly issues a restore when it finds a retired record (`src/Project.cpp:202–215`). The shared upsert's editable comparison ignores lifecycle, and its SQL only switches physical tombstones (state 2) to active, not retired records (`src/internal/RecordSql.cpp:391–406,450–461`). A plain upsert therefore either no-ops or edits the same retired record.

Trigger: create a volume resource, retire it through the ordinary lifecycle API or native `removeProjectResource`, then call Python `add_project_resource` with the same kind/location/owner. The operation returns a UUID without error, but `project_resources` still omits it; the native sibling reactivates the record and makes it visible. This also applies to a matching retired legacy resource selected by the R5 resolver. Test the same no-change and changed-metadata re-add through both APIs, locally and inherited from a referenced store, across owner history modes.

Expected: one shared resource mutation path for native and Python, including lookup, explicit restore, no-op and version guards. If Python intentionally cannot reactivate, reject explicitly instead of reporting a successful add and leaving the resource invisible. This divergence is present at HEAD; R5 centralizes tuple/legacy lookup but not mutation. No runtime test executed.

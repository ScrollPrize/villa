# C-001: Overriding a legacy record can still reorder same-second projects/resources

Source-confirmed residual of the R6 overlay-order fix and a regression against `da50b2f4f` for the case below. The R8 fallback fixes the narrower R7 case where both legacy entries remain in their original owner. No runtime replay.

Take two legacy resources A and B with the same whole-second `createdAt`. A sorts before B by UUID and was also published first (distinct history-on transactions). Attach the owner as a reference and then make a metadata-only override of A. `internal/RecordOverrides.cpp::createRecordOverride` preserves A's creation stamp and before-state version. But `History.cpp::ObjectStore::objectHistory` reads only the winning owner's history; after the edit it returns no history in a history-off root, or a local history whose first publication is not A's creation revision in a history-on root. `Project.cpp::sortByAdded` now gives A the missing-history tie value `INT64_MAX` while B retains its real timestamp, so B takes first place. At `da50b2f4f`, both before and after were UUID-tied and A stayed first for this fixture. This is not a generic legacy ambiguity: original ordering is known before the override and the original owner and version remain reachable through the reference.

`projectResources` and Python `project_resources` use the sorter; `projectRecord` uses it to pick the target of `setProjectName` and the rename part of `copyProject`. A version-1-only filter avoids using override *publication time* as the creation time, but does not preserve creation evidence across a change in the winning owner. The header does document a fallback where history is unavailable; this candidate is the compatibility/stability decision for original history still present in the closure, not an assertion that two truly history-off legacy rows have recoverable chronology.

Validation: compare order before and after a metadata-only override with retained legacy equal timestamps and an unchanged sibling. Cover history-on and history-off roots, local and hosted session reads using that root, and the stable first project after rename. Use separate controls for pure history-off legacy ties, nonoverridden history-on legacy order, and precise current stamps.

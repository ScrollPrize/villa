# C-001: Legacy history-on creation order can change on upgrade

Status: source-backed regression candidate against `1b32f031b`; no runtime replay. R6 explicitly documents a new legacy tie policy, but that policy changes the selected project or first resource on existing stores without any edit.

`Project.cpp::sortByAdded` at the baseline first read the oldest `ObjectRevision::publishedAtUs` from the selected owner, falling back to the whole-second `createdAt` when optional history was unavailable. In the frozen head it orders exclusively by `createdAt`, then UUID. Old writes used whole-second timestamps; separate history-on transactions in the same second have different publication times (`History.cpp::publishHistory` takes microseconds and advances past the prior publication). Create A and then B in separate transactions in that second with A's UUID sorting after B's. The baseline returns A first; HEAD returns B first. This is not the pre-existing history-off tie or the baseline inherited override reordering fixed by R6.

`projectResources` (including Python `project_resources`) exposes the reversal. `projectRecord` returns a different record for a collection with multiple visible project records, so `setProjectName`, and therefore `copyProject`'s rename step, can target a different record. These paths share the sorter for local/reference and packed/sharded readers; hosted project helpers consume it via `readStore`.

Validation: use two retained legacy history-on entries, reversed UUID order, identical legacy creation timestamps, and distinct publication timestamps. Check first resource and selected/renamed project before/after upgrade, with a history-off legacy tie as control. The new mixed-history and override fixture uses current writes with fractional stamps; it does not exercise this upgrade case.

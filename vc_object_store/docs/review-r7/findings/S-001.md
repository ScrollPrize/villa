# S-001 — Initial publication bypasses precise project/resource creation stamps

P2, source-confirmed v21 finalization regression compared with `1b32f031b`. The fix's precision policy is sound for genuinely legacy records, but a current public creation path still produces indistinguishable whole-second stamps.

`src/internal/RecordSql.cpp:426` now requests fractional UTC for project and resource upserts. `src/internal/InitialObjects.cpp:39,51` instead computes a whole-second timestamp for the entire initial batch and supplies it to the same insert helper, regardless of kind. `InitialShardImport::appendObjects/appendObjectRefs` delegates to that path; neither the public initial-object boundary nor its record normalization restricts objects to the AFV kinds. Plain and packed publication preserve the stamp, as do record overrides, closure copies and conversion. `Project.cpp:13–21` treats that stamp as legacy and orders it after every fractional stamp in the same second.

Example: append a volume resource A to a history-off initial shard, then add a volume resource B to a history-on root in the same UTC second, before reading both from their collection. A was written first, but now B sorts first. At the baseline, A's creation fallback was the start of that second and B's history supplied its later publication instant, so A sorted first. This is not the unavoidable ordering ambiguity of two pre-fix coarse timestamps; the current initial writer is still generating coarse timestamps. The same comparison chooses the displayed project record and the record targeted by rename/copy when multiple projects coexist.

Direction: make project/resource creation stamping consistent at both new-row insertion boundaries without rewriting legacy creation data or allocating a second persistent ordering field. Check ordinary and initial creation in both temporal orders, plain and packed/referenced reads, and history-on/off attachments. Check `projectRecord` and `projectResources` with the same shape; neither local Python nor hosted selection owns its own ordering policy. No runtime probe run.

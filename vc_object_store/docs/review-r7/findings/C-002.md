# C-002: Shared resource no-op accepts an unrelated object at the deterministic UUID

Status: Python/direct-store regression candidate against `1b32f031b`, with a pre-existing checked-session sibling defect. Source only.

Seed a live generic object of a different kind at `projectResourceUuid(kind, location, owner)` with the same tags and metadata as the requested resource. This requires no UUID hash collision: public generic upsert accepts client-specified UUIDs. `resolveProjectResourceIdentity` returns the candidate UUID because `currentVersionOf` finds it; `prepareResourceWrite` selects that occupant. `ResourceWrite::unchanged` compares only retired state, tags, and metadata. Native session add returns false, and the new local `addProjectResource(ObjectStore&,WriteTxn&,ObjectRecord)` returns the UUID, although `projectResources` won't list it as the requested kind. Metadata equality is not a valid no-op predicate until the complete kind/location/owner resource identity has been verified.

At baseline the checked session already had the incomplete no-op predicate. Python `add_project_resource` instead called native identity resolution then `upsertObject`, which reaches the explicit immutable kind check in `RecordSql.cpp::upsertObjectImpl`; it rejected this case. HEAD routes Python through the shared early return and bypasses the check. The corresponding new regression should exercise matching metadata at a wrong-kind occupant through Python and checked session (local and referenced), with a correctly matching existing resource as a no-override control. The legacy hash collision guard compares the tuple and is not the failing branch.

# S-008 — Project resource ordering uses incomparable history and direct-mode keys

- Priority: P3 candidate; documented ordering breaks for ordinary referenced stores with mixed retention policies.
- Entry point: `vc_object_store/src/Project.cpp:116–137`, `projectResources`; Python binding advertises results “in the order added” (`vc_object_store/python/objects.cpp:1658`).
- Reachable state: create an older resource in a history-off sealed source; reference it from a history-on overlay and create a later resource of the same kind locally. Both are selected by the logical reader.
- Evidence: a resource with retained publication time is keyed as `("", publishedAtUs)`; an inherited resource without retained history is keyed as `(createdAt, 0)`. The string is compared first, so the later history-on resource sorts before the older history-off resource regardless of their actual times. The analogous project-record selection at lines 83–98 uses zero rather than a creation-time fallback for missing history. Shared owner-specific history lookup is already correct; the problem is how these readers combine its result with the stored creation stamp.
- Shared fix direction: normalize the available publication/creation stamps to a common time representation and use one tie policy in both project lookups. If there is no useful creation stamp, explicitly document the deterministic fallback rather than inventing an age.
- Verification status: static trace; test mixed-history referenced resources and the existing all-history-on/direct paths.

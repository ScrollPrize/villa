# S-010 — Hosted listing catch-up compares raw UUID spellings

- Priority: P2 candidate; exact paged selection can silently lose eligible records after a legitimate concurrent commit.
- Entry points: `vc_object_store/src/client/HostedStore.cpp:438–531` `selectAllObjects` and `selectAllEdges`; also used by `HostedStoreReader` (`vc_object_store/src/HostedSession.cpp:777–783`).
- Reachable state: request an uppercase UUID in the explicit object/edge UUID allow-list of a history-enabled hosted listing, and update that same record between the first listing snapshot and catch-up. The server initially accepts uppercase spellings through binary UUID lookup.
- Evidence: the actual SQLite object selection parses filter UUIDs (`vc_object_store/src/Queries.cpp:54–55`), and edge selection does likewise (`vc_object_store/src/relationships/Edges.cpp:179–191`). Catch-up receives canonical UUIDs in the change feed, but `HostedStore.cpp:410–417` restricts them against uncanonicalized caller strings; a legitimate update then returns no rechecked match. `CatchUp::once` erases all changed keys from the previously matched rows before reinserting matches (lines 379–382). The analogous local string comparisons to a raw `start.afterUuid` in the two hosted requery lambdas can disagree with the original server cursor interpretation.
- Shared fix direction: canonicalize UUID-bearing selection fields once through the existing shared UUID API at the selection boundary used by initial paging and requery. Keep both cursor and allow-list comparisons in the same key form as returned records. Avoid a parallel per-branch string-comparison rule.
- Verification status: static trace. A deterministic regression should arrange an intervening update while paging and compare exact output to the local snapshot using upper/lower-case variants of both allow-lists and cursor IDs.

# S-005: in-place conversion replaces the only legacy database before staging its version mapping

Priority: P2 candidate (publication layering and irrecoverable conversion output on a reporting failure). Baseline `bea32d5d8`. Source trace only; independent adjudication pending.

Locations: `vc_object_store/apps/vc_object_convert.cpp:31–49` prechecks output existence and later writes text reports; `vc_object_store/src/migration/ConvertStore.cpp:940–976` validates a private database then replaces the input before returning `mappingJson`; `vc_object_store/docs/schema-conversion.md:7–17` describes the supported `--in-place` command and revision-to-version mapping.

Trigger: use the supported in-place conversion with a mapping path whose parent does not exist, or encounter a mapping-file write failure. The current precheck only rejects existing/symlink or duplicate output paths, so a missing parent passes. The migration publishes schema 21 over the original legacy file, returns the mapping in memory, and then the CLI attempts the mapping stream. The CLI exits with an error, with the input already converted and the requested mapping absent or partial. Reinvoking the legacy converter on that now-current input cannot recreate the original legacy revision mapping. No failure of SQLite validation is needed.

Expected: the layer controlling irreversible in-place publication should prepare the required mapping output before discarding the legacy input, and publish each report through the shared safe file writer. A predictable invalid output destination should fail before replacement. This does not require impossible atomicity across arbitrary independent files; it requires a recoverable publication order and clear distinction between conversion failure and a post-conversion reporting failure. A leftover complete sidecar can be explicitly handled; losing the only mapping in process memory after replacing the input is not equivalent.

Shared fix direction: integrate report/mapping staging with the existing migration publication boundary (or an explicit prepared-result hook) rather than a second unchecked publication protocol in the CLI. Reuse the shared staged file/no-clobber path and retain the documented no-overwrite behavior. Do not silently force multi-file transactions or automatically delete user reports.

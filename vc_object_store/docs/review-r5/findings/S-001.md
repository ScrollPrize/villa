# S-001: hard-linked database aliases bypass the service ownership guard

Priority: P2 candidate. Frozen baseline `bea32d5d8`. Evidence: source trace only; no runtime reproduction. Independent-model adjudication pending.

Locations: `vc_object_store/src/internal/Ownership.cpp:20–27,72–86`; writable-open/service-owner setup in `src/Database.cpp`. `guardPath` uses weak canonical path spelling plus `-owner`; that resolves symlinks but not hard links to one physical SQLite file.

Trigger: create an ordinary hard link `alias.vcobj` to `served.vcobj`, start `vc_object_server` against `served.vcobj`, then open `alias.vcobj` writable through the standalone API. The service locks `served.vcobj-owner` exclusively while the other handle takes a shared lock on a different `alias.vcobj-owner` file. Both ownership checks succeed although both write the same database inode.

Expected: the documented host-local service-owner exclusion applies to the database, not only one pathname. The native opening contract says a served store rejects other writable opens. Existing export destination protection recognizes hard-link equivalence, so alias treatment is inconsistent at the shared ownership boundary. This finding is about the ownership-enforcement contract; it does not claim a demonstrated SQLite corruption or a bypass through ordinary identical/symlink paths, which are handled.

Shared fix direction: resolve/guard physical file identity consistently, or explicitly reject multiply linked writable files if physical identity cannot be safely guarded portably. Do not add consumer-specific checks to server and CLI callers. Preserve Ubuntu/macOS behavior and clarify the intentionally host-local scope. A regression should hold the service guard on one hard-link spelling and require the other writable spelling to fail while readonly access remains usable.

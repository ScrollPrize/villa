# S-003: published catalog cache bypasses checked file publication

Priority: P3 candidate (I/O failure path). Frozen baseline `bea32d5d8`. Evidence: source trace; no runtime or disk-fault injection. Independent adjudication pending.

Locations: `vc_object_store/src/catalog/CatalogStore.cpp:199–211,303–306`. Reachable via `fetchPublishedFile` from `volume-cartographer/apps/VC3D/overlays/InkDetectionOverlayController.cpp:401`; catalog unit test exercises successful caching at `vc_object_store/tests/cpp/test_object_store_catalog.cpp:276–279`.

Actual: a private `std::ofstream` receives the downloaded bytes, then checks stream state before its destructor closes/flushed the stream. A failure while flushing a buffered tail or closing the file is not checked, and the subsequent rename can publish an incomplete file. Failed writes/renames also leave the `.partial-...` file behind. Future `fetchPublishedFile` calls trust any regular target file, so successful rename after an unnoticed close failure can make a broken cache entry persistent across retries.

Expected: publish only fully written cache files; discard private staging on failure. This is ordinary local I/O handling, not a claim that a particular network response or catalog artifact is currently broken.

Shared fix direction: use `vcr::AtomicFile`/`atomic_write`, already used in vcobj artifact and AFV report publication, rather than another custom buffered-close/rename protocol. Preserve the existing cache hit/no-redownload contract. If adding a fault-injection regression, verify both no published target after the failed first download and cleanup of the partial file. Avoid changing the broader remote surface format contract from rejected R4 S-001.

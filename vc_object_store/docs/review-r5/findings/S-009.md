# S-009 — Project resource identities do not encode field boundaries

- Priority: P2 candidate; distinct supported records share a logical key.
- Entry points: `vc_object_store/src/Project.cpp:148–167`, public `projectResourceUuid` and `projectResourceRecord`, reused by native and Python add-resource APIs. `vc_object_store/docs/writing.md:255–260` describes deterministic identity and shared versus per-owner records.
- Reachable state: register a shared volume at `/datasets/owner/alice` and a private volume at `/datasets` with owner `alice`. Both are allowed location strings and can be distinct valid datasets.
- Evidence: the raw concatenation at line 150 hashes the identical name string for both tuples. Native add/update at lines 175–182 reuses the resulting current UUID rather than creating a second logical object. Depending on the write path, this replaces a resource or rejects its separate registration; the two cannot coexist, and viewer filtering may hide the shared resource.
- Shared fix direction: one unambiguous tuple encoding in the shared identity API, with an explicit legacy lookup/compatibility policy. At minimum detect incompatible fields before updating an occupied legacy key. Do not add consumer-specific aliases.
- Verification status: static trace; compare the returned IDs and check shared/private visibility through both API bindings.

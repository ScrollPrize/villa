# P-003: Python bindings maintain a second anchor schema codec

Priority: P3 architecture candidate, not a demonstrated corruption bug. Baseline `bea32d5d8`; code comparison, no runtime reproduction. Astra adjudication pending.

Locations: `vc_object_store/python/StorageBindings.hpp:67–112` (`anchorFromPy`, `anchorToPy`), consumers at 179–192 and 287; shared native `vc_object_store/src/internal/Anchors.cpp:78–128` (`dependenciesFromJson`, `anchorFromJson`, `anchorToJson`), used for record/request JSON at `src/internal/RecordJson.cpp:143–144`.

Actual: the Python adapter repeats the full list of schema keys, dependency point fields, optional vector shapes and serialization decisions. It shares only the final semantic `validateAnchor`. The local typed write path and hosted/JSON path can therefore evolve separately. One present difference: the Python helper treats dependency fields such as `channels=None` as omitted via `has`, whereas the JSON dependency parser attempts a vector conversion on explicit null. That illustrates drift, but null handling might intentionally be Python convenience rather than a supported wire input; no production failure from it is claimed.

Expected abstraction: native anchor schema interpretation, validation and serialization have one implementation. Python-specific conversion (including deliberate None handling or numeric/sequence adaptation) should remain at the language boundary, not duplicate which anchor keys mean geometry/metadata dependencies. Use a shared normalized descriptor or existing codec with intentional adapter normalization; preserve supported Python types and native numeric semantics. Do not replace efficient array/byte bindings with JSON just to eliminate legitimate transport adaptation.

Evidence is the two independently maintained schema codecs and observable conversion difference. The reviewer should classify it as architectural duplication if confirmed, and not count it as a correctness defect absent a common documented input that fails.

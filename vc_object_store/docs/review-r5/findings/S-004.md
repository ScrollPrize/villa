# S-004 — Copy unseals single-shard immutable initial stores

- Priority: P2 candidate; supported copy fails before publishing.
- Entry point and contract: `vc_object_store/src/ObjectCollection.cpp:602` public `copyObjectCollection` promises an independent mutable copy of plain, packed, referenced or sharded stores (`vc_object_store/docs/collections.md:91`).
- Reachable state: build a valid initial-import collection with one shard, then call the collection-copy API. The physical root is sealed with the immutable-initial required feature and there are no same-store partition members.
- Evidence: `ObjectCollection.cpp:614–617` chooses the mutable-overlay path only for same-store partition members. The other path copies the root, forks storage identity, and writes `sealed=0` without removing the feature (`ObjectCollection.cpp:647–660`). Staged verification at line 667 uses the ordinary opener, which rejects an unsealed immutable-initial root even when opened read-only (`vc_object_store/src/Database.cpp:84–87`). A multi-shard input retains the sealed root behind a new writable overlay (lines 663–666).
- Shared fix direction: use the store's immutable provisioning state as well as partitioning to choose the existing sealed-source overlay-copy path. Do not weaken the physical open guard or synthesize mutable history/index tables in an immutable payload store.
- Verification status: source trace only. Regression should copy and reopen an initial import with one shard and verify a real edit through the new writable overlay without changing the original.

`src/internal/Ownership.cpp:20` derives a guard filename from `weakly_canonical(absolute(store))` plus `-owner`. The POSIX implementation opens that separate file and uses `flock`; it does not lock or compare the underlying database inode. Two hard-linked ordinary database paths consequently produce different owner guard files, unlike symlink aliases. `src/Database.cpp:98` acquires this guard for writable ordinary opens with service or standalone mode, with no hard-link exclusion at that boundary.

The documented contract in `docs/reading.md` is that a store owned by its hosting service rejects standalone writable opens. Using two ordinary hard-link spellings permits both ownership guards to succeed for the same physical database. This is an exclusion-boundary defect, irrespective of whether SQLite later serializes a particular attempted write or reports a busy database.

Qualification: arbitrary raw-file mutation is outside the API's protection, and simultaneous alias-path SQLite use has additional hazards; neither is required to show this guard bypass.

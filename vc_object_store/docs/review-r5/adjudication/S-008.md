# S-008 adjudication

Decision: **confirmed defect, P3**. Independent GPT-6 Astra source review at `bea32d5d807731d8c3b2db17c815cde748523226`; no project/runtime reproduction.

`projectResources` in `src/Project.cpp:116` declares the actual ordering cache as `std::map<std::string, std::pair<std::string,int64_t>>`. History-backed rows receive `("", publishedAtUs)` and history-off/unpublished rows receive `(createdAt,0)`. Sorting compares these pairs lexicographically before UUID. Thus any history-backed row precedes a fallback row with a nonempty creation string, regardless of age. These are genuinely incomparable representations, not multimap overwrite semantics.

An older resource inherited from a sealed history-off source and a later local history-on resource are both legal logical results. The later row sorts first, contradicting the native comment and Python `project_resources` promise of added order at `python/objects.cpp:1658`. Owner-aware optional history lookup itself is correct. `projectRecord` has the related fallback-to-zero ordering problem when selecting among multiple projects.

Qualification: no permission, geometry, or data-loss effect is asserted; P3 reflects ordering/selection behavior. Ordinary timestamp-bearing records provide a sufficient counterexample without inventing missing timestamps. Normalize available timestamps in one shared ordering policy, define deterministic unknown-time behavior, and avoid imposing a fictional combined publication timeline. Distinct from S-009's identity collision in the same file.

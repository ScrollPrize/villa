`src/ObjectCopy.cpp:12` refuses a source when `StoreReader::status().extensionsPresent` is true. `LocalStoreReader::status` delegates to `ObjectStore::status`, whose implementation in `src/Versions.cpp:466` calls `hasExtensionTables(db)` only on its physical root connection. The later metadata guard only recognizes `vcobj_extensions`. `readObjectCopy` otherwise copies core record fields, geometry, and point annotations; it has no extension-row copying operation. The session import/copy path calls this helper.

A sealed source with a colocated unversioned initial extension and an ordinary extension-free referencing root is permitted by `docs/extensions.md`. Such immutable result rows need not produce a versioned metadata snapshot descriptor. Reading/copying the inherited object through the root bypasses both rejection guards even though copying directly from its owner is rejected. The documented selected-object-copy policy is to refuse unsupported extensions, not silently omit them.

Qualification: this is a placement-dependent preservation-check defect, not a demand that core geometry reads expose extension data, or a claim that all registered extensions necessarily belong to the copied object. An explicit conservative closure check or selected-owner preservation policy is needed. Hosted extension-row APIs remain unsupported; they must not silently advertise complete copying either. Distinct from C-006's destructive refresh of an existing record.

# Packed stores

Packed storage is optional. Ordinary schema-22 databases remain ordinary SQLite files. `PackedStore.hpp` provides a builder and a SQLite VFS for a container of independent databases; the container format version is separate from the vcobj logical version and SQL schema version. Store references (`store_reference`), table routing, shard ownership, and lineage UUIDs and commit sequences remain in the vcobj manifests rather than the VFS.

## Creating and reading

Create `PackedStoreBuilder(destination, options)`, call `addDatabase(databaseUuid)` for each independent database, and pass the returned locator to `ObjectStore::create`. Each worker may write a different database; ordinary SQLite single-writer locking still applies within each database. Close every store/SQLite connection before `finalize(rootDatabaseUuid)`. Finalization compacts by default; pass `false` to retain extent allocation. A failed or abandoned build cleans its private sibling staging files and never publishes incomplete contents. As with any durable publication, an error syncing the directory after publication can leave the complete destination visible; the caller must treat that durability error as an uncertain completion, not blindly overwrite it. The builder must outlive its connections. Published containers cannot be edited; create a new overlay store instead.

`importDatabase(uuid, source)` uses SQLite's backup API, obtaining a consistent snapshot including committed WAL data. This copies a database, not its external referenced stores. `compactPackedStore(source, destination)` repacks all members into contiguous ranges without changing the source; SQLite freelist pages are not removed. Destination paths must be new. Imported databases retain their logical IDs and metadata. Creating an ObjectStore member directly sets its physical `database_identity` UUID from the builder locator. For imports, use the source's existing database UUID. `packedMemberReference(uuid)` produces a portable `@packed:UUID` manifest reference; `resolvePackedDatabasePath(context, reference)` resolves it against the current container or builder rather than saving an absolute/staging path.

Database-copy finalization also copies the source artifact sidecars, including retained historical payloads, and verifies their hashes. The destination sidecar is prepared before the database becomes visible and removed if publication fails. Existing destinations are never overwritten. Artifact payloads remain in the normal `.artifacts` sidecar, not inside the packed SQLite container; move that sidecar with the container. External source files named by `storage_ref` are not implicitly copied.

`ObjectStore::open(containerPath, readOnlyOptions)` recognizes the packed header and opens the logical root, including its partition/reference scope. `packedDatabasePath(containerPath, databaseUuid)` returns a locator for another member. `packedDatabases` lists directory entries. Direct SQLite users pass the locator and `packedStoreVfs()` to `sqlite3_open_v2`; published databases require `SQLITE_OPEN_READONLY`.

`packObjectCollection(source, destination, options)` packages a sealed collection and its complete store_reference/partition dependency closure into one compact container. It copies each independent database, rewrites only physical member locators to `@packed:UUID`, and validates the rewritten store_references before finalization. Logical identities, commit sequences, histories, and sealed dependency pins are retained. The result can be moved independently of the original directory. This full-closure operation intentionally copies referenced bases; to retain thin external store_references instead, construct a new packed root with `ObjectCollection::create` and reference the existing sealed bases.

Building databases use rollback journals, not WAL. `ObjectStore` chooses `journal_mode=DELETE` automatically for builder locators. Backup imports materialize all committed pages and then set the private checkpoint's SQLite header read/write-version bytes to rollback-journal format before reopening it; no WAL sidecar is needed. Direct SQLite callers should also use `temp_store=MEMORY`; anonymous temporary files are not supported by the packed VFS. There is no cross-member transaction or restart/recovery protocol for unfinished imports. A crash before final publication requires rebuilding the import. SQLite `xSync` persists the member's preceding dirty data plus the backing file unless `disposableBulk=true` was explicitly requested. Finalization always syncs and durably publishes, even in disposable mode.

## Buffering

The default bounded-cache policy can perform synchronous I/O on dirty eviction and on writes to already evicted extents. `disposableBulk` alone suppresses sync requests, not those writes. Set `memoryFirst=true` together with `disposableBulk=true` for a strict RAM-first import: every live extent remains resident, including journal data and sparse extensions, and producer read/write/sync calls never spill or reload backing payload. `residentBytes` is a hard live-extent budget. Exceeding it returns `SQLITE_FULL` with a `packedStoreLastError()` message identifying the memory budget, poisons the builder, and prevents publication; it never silently changes policies. Choose a budget covering the complete output working set plus simultaneously live rollback journals, not merely SQLite's page cache. This is an explicit opt-in: the default 256 MiB budget is not appropriate for a full-volume memory-first import.

`backgroundFlush=true` (default) allows asynchronous persistence while RAM-first producers continue using retained bytes. Rewrites remain resident and journal retirement defers physical address recycling until outstanding snapshots finish without making producers wait for those writes. Set `backgroundFlush=false` to defer all payload persistence until `finalize()`; construction still creates a sibling staging file and writes its 80-byte invalid header. No background writer is started in this mode. Closing SQLite connections does not publish or flush a memory-first import; close them all, then explicitly call `finalize()`. Finalization joins any worker, writes remaining data, syncs and publishes. Compact memory-first finalization writes directly from resident bytes into the compact target rather than flushing to staging and rereading the complete dataset first. Aborting the builder discards unpersisted data and removes its private files. Background failures are propagated before publication. Report RAM ingestion and final persistence/publication durations separately; ingestion alone is not durable throughput.

Turning off `backgroundFlush` is also supported with the bounded policy, but does not suppress its synchronous eviction I/O. Memory-first's payload guarantee does not remove ordinary CPU/memory contention: brief mutex-protected byte copies and background snapshot construction still take time.

Compact publication assigns deterministic, disjoint contiguous ranges before copying. `exportWorkers` defaults to one and must be positive. Exports of at least 8 MiB may use the requested number of independent writers, limited by member count, hardware concurrency, and the number of extents in the resident budget. Each writer has its own native file handle; all writers finish before the final directory, checksum, sync, and atomic publication. `preSizeExport=true` optionally sets the compact target's logical payload size before copying; this is sparse sizing, not physical preallocation, and defaults to false. Measure these options on the destination filesystem: concurrent writes into one inode need not outperform sequential writes. Resident bytes are copied straight to the compact destination in both buffering policies, without writing and rereading an intermediate staging copy. Queued staging writes are skipped at compact finalization; an already-running snapshot finishes before export begins. Evicted data is read through a per-worker scratch buffer allocated only when needed. A writer error prevents publication and the builder cleans its private files.

Strict RAM-first allocation reserves its byte budget under the shared lock, then initializes private extent memory outside it. With background flushing disabled, resident reads and writes similarly copy under only their logical member's operation lock; independent shards do not serialize payload copying. Budget accounting, member sizes, and global bookkeeping remain protected, while bounded-cache eviction and background-snapshot paths retain their existing synchronization.

The default extent is 4 MiB, with a 256 MiB resident budget. Extents must be power-of-two sizes between 1 MiB and 1 GiB, and the budget must hold at least one extent. Each database and its rollback journal have independent logical address spaces. A dirty queue feeds the background writer; an LRU list tracks resident extents without scanning the complete database directory. Dirty extents can be evicted synchronously under memory pressure; clean extents are retained until needed. Once an extent is persisted and evicted, ordinary reads/writes pass through only their requested byte range rather than reloading a complete extent; SQLite retains its own page cache. Such direct I/O cannot race an asynchronous snapshot because in-flight extents are never evicted. Truncation clears retained tail bytes so a subsequent extension cannot expose stale contents. Deleted journals and truncated extents return physical space to a free list only after their in-flight writes finish, avoiding accumulation of journal-sized holes after every transaction.

Each background write snapshots dirty 4 KiB subranges and the extent's write counter, coalescing adjacent subranges. The first persistence initializes the entire extent, including recycled addresses and zero tails; subsequent small SQLite page writes do not rewrite a complete MiB extent. Completion only records that version as flushed; later writes remain dirty. An in-flight extent cannot be evicted until its write completes. RAM usage is the configured resident budget plus at most one extent-sized background snapshot during ingestion, up to one extent-sized scratch buffer per export worker during bounded-cache finalization (none for memory-first compact export), directory bookkeeping, and SQLite's own page caches. Physical I/O uses the platform SQLite VFS. Publication atomically creates a hard link from the completed sibling staging file to the new destination, then syncs the directory with vc_reader's portable platform helper and removes the staging name. This avoids an overwrite race; the destination filesystem must support hard links. This is anonymous-memory write buffering, not writable mmap, so the container's resident budget is explicit.

Direct nonresident I/O reserves its extent while releasing the shared cache mutex. Each logical member has a separately serialized native file handle, allowing independent shards to perform page I/O concurrently without assuming a platform VFS supports concurrent calls on one handle. Truncation and retirement cannot reuse an extent during outstanding I/O. Strict sync still flushes the underlying file; disposable imports defer durability only until finalization.

## Container format 1

Integers in the fixed header are unsigned 64-bit little endian. The 80-byte header contains the 8-byte magic `VCOBJPK2`, container version at byte 8, directory offset at byte 16, directory byte length at byte 24, SHA-256 of the directory bytes at bytes 32–63, and zero reserved bytes 64–79. During construction the header is zero and therefore not a valid published container. The complete directory and payload are synced before writing the final header.

The directory is UTF-8 JSON at the end of the file, capped at 256 MiB. It contains `root` (database UUID), `extent_bytes`, and a `databases` array. Each entry contains `uuid`, logical `size`, `contiguous`, and `offsets`. For an extent-mapped database, `offsets[i]` locates logical extent `i`, each extent occupies `extent_bytes`, and the last logical extent may be only partially used. For a contiguous database, `offsets` contains a single start offset and the range is exactly `size` bytes. Zero-length contiguous members still have one start offset. Readers reject duplicate UUIDs, overlapping extents, out-of-bounds ranges, unsupported versions, invalid extent counts, a missing root, truncated directories, and directory checksum mismatches.

The checksum covers directory integrity, not every payload byte. SQLite integrity checks and application-specific validation remain separate. Container allocation slack is removed by compact export; arbitrary SQLite freelist slack is not. Runtime dirty/LRU/version state and rollback journals are not included in the published directory.

## Validation

The `test_packed_store` C++ target exercises independent concurrent database writes, member locking, rollback, repeated writeback rewrites, bounded-cache eviction/reload, partial writes, truncation and zero filling, strict sync, compact reopen, history-off creation through the VFS, automatic root opening, committed WAL-source backup, abort cleanup, failed publication without clobbering existing data, and malformed/truncated directory rejection. Memory-first coverage verifies that the backing file remains header-only throughout ingestion with background persistence disabled, budget exhaustion fails rather than spills or publishes, truncate/reextend retains zero-fill semantics, and concurrent background rewrites/journal retirement survive noncompact publication. Test files are owned by the suite's RAII temporary directory and are removed on both success and failure.

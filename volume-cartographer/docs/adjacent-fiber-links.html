Adjacent fiber links

Proposal for PR #1829: adjacent links live in their own top-level adjacent_branches array. The array name is the kind; entries have exactly the existing branches schema.

What it means

An ordinary link ties two control points to the same winding of the sheet. An adjacent link ties a vertical fiber to a horizontal fiber one winding outside it: WV = WH − 1. The effective H/V tags determine which side is inside. An adjacent link between fibers that are not one H and one V remains stored, is flagged as an error in the fiber map, and contributes no winding constraint.

The file format

Ordinary links appear only in branches. Adjacent links appear only in adjacent_branches. Both entries of a reciprocal pair live in the same array on their respective files. There is no per-entry adjacent field.

{
  "branches": [],
  "adjacent_branches": [
    {
      "branch_control_point_direction": [-0.024412605581528416, 0.13769928147742536, -0.9901731831196608],
      "branch_control_point_index": 0,
      "branch_control_point_position": [12871.478552834642, 10018.210630149675, 16662.399929928943],
      "branch_fiber_id": 220,
      "branch_file": "auto_20260911T045455583_000007.json",
      "control_point_direction": [0.9963752036835241, 0.058142649700040565, 0.06209577900690697],
      "control_point_index": 0,
      "control_point_position": [12867.714596623457, 10041.881788022982, 16661.818795840572],
      "pending": true
    }
  ]
}

Link fields excerpted from a real open-data fiber entry. Other top-level fiber fields are omitted. Floats retain full precision; the runtime branch_fiber_id is rebound from branch_file at load. Approval removes pending as it does for an ordinary link.

Array presence is the compatibility signal

A current VC3D writer always writes adjacent_branches, including an empty array when there are no adjacent links. The sync merger also writes the array on merged documents and rewritten peers, after checking for a legacy regression.

Array stateMeaning
AbsentA legacy writer saved this file; it cannot express a decision about adjacent links.
Present, emptyA writer that knows the kind deliberately has no adjacent links.
Present, nonemptyThese entries are the adjacent links.

The strip check is simply “the base had adjacent entries, and this side lacks the array.” It runs before merge shortcuts and before vc_sync plans a plain local upload. An empty base array proves no lost links. Moving anchors or deleting ordinary links cannot hide a stripped nonempty array.

Changing kind requires deleting and re-linking: the entry moves from one array to the other and starts pending again. The merge treats that as deletion of the old kind plus addition of the new kind. A deliberate re-link replaces the old review state; concurrent additions with different kinds at the same anchors conflict.

Loading and reciprocal repair

VC3D reads both arrays into its existing in-memory branch references, with the kind derived from the containing array. Its pairing predicate requires the same kind, reciprocal control-point indices, matching positions and compatible directions. An ordinary ref never satisfies an adjacent ref's reciprocity check.

Before any cross-file validation or broken-link repair, the loader restores an adjacent reciprocal into a peer whose array was absent. It leaves a peer whose array was present alone, including an explicitly empty array. Multiple peers can restore entries into the same legacy file. Source-qualified paths prevent a working copy from healing a different copy with the same filename.

A restored peer is marked for saving; the save is skipped if the file changed on disk since it was read. Healing must precede validation: otherwise the missing reciprocal can cause the strict loader to remove an entire connected network from the session.

fiber_merge runs the same branch merge, anchor rebinding, peer discovery, review-state refresh and base-aware reciprocal deletion machinery over both arrays. The merged file's decisions determine its peers' same-kind reciprocals. A base-authorized re-link moves the peer's entry between arrays. Without a base, a different-kind reciprocal is a conflict, not a pairing. A conflict leaves the peer unchanged.

What old software does

ConsumerBehavior
spiral-fitting, vesuvius loader, HF publishingRead branches and never see adjacent links. They cannot mistake these links for same-winding links or fuse the two windings through them. No changes to those readers are required.
Old VC3DIgnores adjacent_branches on load. It rebuilds the JSON from its own fields on save, dropping the array. A surviving reciprocal lets the current loader restore it; a synced base with adjacent entries lets the current merger or upload guard detect the loss.
Old fiber_mergeCarries the array from whichever side it copies and does not merge the other side's changes to it. Array presence cannot detect this stale carry-through.
The remaining rollout question is the old merger: a hard version fence would have to make it reject the file. This proposal does not bump the fiber format version. If old VC3D saves both endpoints and no current sync base or surviving reciprocal remains, the lost adjacent links cannot be recovered from those files alone.

Map, solver and GUI

The existing map, solver and GUI behavior stays: adjacent candidates and links use triangles, created links are pending, H/V tags determine the one-turn offset, and adjacent links do not certify kollesis seams. The map's kind-disagreement flag remains available and such a disagreement contributes no winding constraint. Normal file loading additionally enforces same-kind reciprocity before a network reaches the map.

Verification

Python regressions exercise both arrays, missing versus empty, legacy saves on either or both sides, shortcut paths, re-links, approvals, geometry rebinding, opaque entries, peer discovery and reciprocal refresh.

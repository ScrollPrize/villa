# Draft opt-in verification of CT reads

This CPU-only opt-in draft targets Villa base `417e17689029434fa1572efe20a3e7a9bfc79be4`. It leaves the default read path unchanged. Production activation requires a caller-side ledger acceptance gate and review of the exact application integration.

Repeated whole-volume verification of a restored CT dataset dominated preparation of small real scroll crops. The optional reader verifies the same owned compressed bytes returned to the decoder, using a complete immutable manifest. With no opt-in environment the existing read path remains unchanged. OpenSSL Crypto supplies SHA256; no custom digest implementation is introduced.

Set all three environment variables together: `VC_VERIFIED_CT_MANIFEST`, `VC_VERIFIED_CT_MANIFEST_SHA256`, and a fresh owned `VC_VERIFIED_CT_LEDGER`. The manifest schema is `verified-ct-read-manifest-v1`, with canonical `volume_root`, complete `objects` records containing `key`, `absent`, `bytes`, and `sha256`, and `max_chunk_bytes` in the range 1 byte through 32 MiB. The retained CT manifest declares a 2 MiB limit and its largest present chunk is 2 MiB; the compiled 32 MiB ceiling gives 16x headroom while bounding the per-read buffer allocation. This is a CT-specific bound, not a promise to accept arbitrarily large Zarr chunks. Explicit absence is separate from a missing/unlisted object. Protected shard and mmap entry points reject rather than bypass verification. The caller must keep the volume tree immutable throughout guarded reads: the guard rejects symlinks it observes and verifies the digest of the exact owned bytes it returns, but does not claim race-free filesystem confinement against concurrent path replacement. With `VC_VERIFIED_CT_MANIFEST` enabled, Store-backed Zarr access is rejected process-wide: Store open overloads do not yet have a canonical array root to check, so the restriction also applies to unrelated Store roots. This opt-in supports the guarded filesystem Zarr2 G0 path; remove all three opt-in variables to use stock Store access. This is not universal I/O interception.

A renderer may catch decoding exceptions and zero-fill. Therefore a production caller MUST audit the ledger before accepting science: exact INITIALIZED manifest binding, nonzero VERIFIED read coverage, no REJECTED event, and bounded complete evidence. Mandatory evidence infrastructure failures terminate with code86 without a core dump. The standalone library cannot make an application-level acceptance decision on a swallowed read failure.

## Tests and real-data evidence

Enable the existing CMake `VC_TESTING` option and run `ctest -R verified_ct_read --output-on-failure` after building `test_verified_ct_read`. Tests exercise actual public Zarr API calls, exact bytes, mutation/size/absence, forbidden bypasses, mandatory evidence failures, both Store-open overloads with a real unrelated `FileSystemStore`, and stock Store reads in children with all opt-in variables removed. The earlier focused central CMake/CTest run passed the original fixture (1/1 CTest, 18 public-API cases) against the separately qualified imported library; it did not run this revised fixture or configure the full repository. Re-run the revised CPU-only fixture in the PR build environment. macOS/arm64 are not qualified.

Earlier real-data qualification and nine-pair results belong to older source revisions and are not evidence for this final combined patch. The final-source CPU-only comparison used three AB/BA/AB pairs on two fixed crops; all six arms passed exact complete-tree comparison. Median stock/candidate times were 52.690/5.052 seconds (27×180×1060; 10.43×) and 54.203/5.558 seconds (27×180×4640; 9.75×); summed two-crop pair ratios were 9.64×, 9.71×, and 10.08×. These are fixed-workload CPU preparation observations, not GPU, full-pipeline, or universal speedups. PawPad services and a production controller/validator were active during measurement, limiting timing precision. The final-source-v2 summary, receipt, and linker proof are retained separately in the takeover evidence workspace.
